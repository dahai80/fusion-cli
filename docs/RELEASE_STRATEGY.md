# Release Strategy — Canary & Gray Release

> #54 enterprise blocker: canary/gray-release for the `fusion` binary.
> This is a **CI/CD-layer** concern (GitHub Actions + release tooling), not CLI
> source code. The CLI itself is release-agnostic; this doc defines the rollout
> pipeline that ships it safely to production users.

## Status

**Owner:** CI/CD + release engineering (not `fusion-cli` Rust code).
**Scope:** GitHub Actions release workflows, GitHub Releases, distribution
channels (Homebrew tap, direct binary download), rollback procedure.

## 1. Release Channels

Three release channels, mapped to git tag prefixes and GitHub Release
`prerelease` flags. Users opt into a channel by installing from the matching
tag pattern.

| Channel | Tag pattern | GitHub prerelease | Audience | Stability |
|---------|-------------|-------------------|----------|-----------|
| `stable` | `vMAJOR.MINOR.PATCH` | no | all users | production-ready, passed full CI + canary gate |
| `canary` | `canary-vMAJOR.MINOR.PATCH-YYYYMMDD-SHORTSHA` | yes | opt-in testers | bleeding edge, newest commit, may regress |
| `beta` | `vMAJOR.MINOR.PATCH-beta.N` | yes | opt-in early adopters | release-candidate, feature-complete, stabilization phase |

Promotion path: `canary` → `beta` (after N canary deployments pass gates) →
`stable` (after beta soak period with no blocking issues). No channel skips
`canary` — every stable release was a canary first.

## 2. Semantic Versioning & Tag Policy

Follow [SemVer](https://semver.org/) strictly. Version source of truth is
`Cargo.toml` `[package].version`; the tag MUST match it exactly.

- **Patch** (`0.3.5` → `0.3.6`): bug fixes, security patches, no new API.
  Trigger: P0/P1 fix merged to `main`.
- **Minor** (`0.3.5` → `0.4.0`): new subcommand, new config section, backward-
  compatible. Trigger: new feature merged.
- **Major** (`0.3.5` → `1.0.0`): breaking change (config schema, CLI flag
  removal, removed subcommand). Requires migration guide in CHANGELOG.

Tag naming:
- `stable`: `v{version}` (e.g. `v0.4.0`). Annotated tag, signed if a release
  signing key is configured.
- `canary`: `canary-v{version}-{YYYYMMDD}-{SHORTSHA}`. Lightweight tag,
  auto-generated by CI on every push to `main` that passes CI. Never reused.
- `beta`: `v{version}-beta.{N}` where N increments per release-candidate
  rebuild. Stable tag replaces the final beta tag (e.g. `v0.4.0-beta.3` →
  `v0.4.0` on promotion).

Rules:
- One tag → one immutable GitHub Release with attached binary artifact.
- Never move or re-tag. A bad release gets a new patch tag + a retraction note.
- `Cargo.lock` (committed per #53) guarantees the exact dependency tree the
  tag was built against is reproducible.

## 3. Canary Pipeline

Goal: catch regressions on a small cohort *before* they reach all users. The
`fusion` binary is a local CLI with no central telemetry sink, so "canary
cohort" = users who opt into the `canary` channel, and "metrics" = opt-in
crash/error reports + issue tracker signals.

### Staged rollout

Each promotion is a **gate**, not a time box. Do not advance until the current
stage passes.

1. **CI green** — `check`, `test`, `fmt`, `clippy`, `deny`, `build` all pass
   (existing `.github/workflows/ci.yml`). Required for any tag.
2. **Canary build** — `release-canary.yml` builds on push to `main`, publishes
   a `canary-*` GitHub prerelease with the binary artifact.
3. **Canary soak (≤24h)** — opt-in testers run the canary binary. Maintain a
   `canary` issue label; any new `bug`-labeled issue against a canary tag
   blocks promotion.
4. **Beta promotion** — if canary soak is clean, cut a `v*-beta.N` tag. Beta
   users (broader opt-in) install it. Soak 24–72h.
5. **Stable promotion** — if beta is clean, cut the stable `v{version}` tag.
   GitHub Release marked non-prerelease. Distribution channels (Homebrew tap,
   direct download) point at the latest stable tag.

### User opt-in

Installation channel is a *user choice*, never forced. Users pin a channel via
their install command (e.g. `brew install fusion-cli@canary` vs `@stable`).
The CLI config (`~/.fusion/config.toml`) is channel-agnostic — no "channel"
field is needed; the running binary version (from `fusion version`) is the
source of truth.

### Auto-halt conditions

Promotion is blocked if ANY of:
- A `bug` or `security` issue references the candidate tag and is still open.
- `cargo deny check advisories` reports a new un-ignored CVE (from #53 guard).
- A known P0/P1 regression from the prior release is not fixed in the
  candidate.

## 4. Gray-Release Mechanics

Gray release = gradually exposing a new version to an increasing fraction of
users *within the stable channel*, not just via a separate canary channel.
For a local CLI without a central update server, percentage-based distribution
is approximated through the **distribution surfaces**, not in-binary rollouts.

### Distribution surfaces

1. **Homebrew tap** (`homebrew-fusion`): the stable formula's `version`/`sha`
   fields point at a GitHub Release asset. Gray rollout = delayed bump: keep
   the formula pinned to the *previous* stable tag for the first N hours after
   a new stable tag lands, then bump. This gives a manual soak window.
2. **Direct download** (`install.sh` fetching `https://.../releases/latest`):
   `releases/latest` follows the newest non-prerelease GitHub Release, so it
   flips immediately. To gray-release here, the install script can check an
   opt-in `FUSION_RELEASE_CHANNEL=canary|beta|stable` env var to select the
   tag pattern, defaulting to `stable`.

### Cohort selection

No random percentage split is possible client-side without a telemetry loop.
The practical cohort boundaries are:

- **canary cohort**: users who set `FUSION_RELEASE_CHANNEL=canary` or install
  `@canary` — self-selected, tolerant of breakage.
- **beta cohort**: `FUSION_RELEASE_CHANNEL=beta` / `@beta` — early adopters.
- **stable cohort**: default, everyone else.

### Feature flags

New *risky* CLI features (not yet stable) should land behind a config flag
default-off, e.g. a `[experimental]` section in `config.toml`, rather than
behind a release-channel gate. This keeps the channel mechanism about
*version stability* and the flag mechanism about *feature exposure* — two
orthogonal axes (Rule 7: surface conflicts, don't average them).

### Why not in-binary rollout

A local CLI has no heartbeat to a server, so the server cannot push a version
to X% of installs. Attempting to fake it (e.g. `fusion upgrade` rolling dice
client-side) is non-deterministic and unobservable (Rule 5: decide with code,
not tokens — and this isn't even a model decision, it's just unmeasurable).
The channel + delayed-formula approach is the honest equivalent for this
deployment model.

## 5. Rollback Procedure

Two rollback tiers depending on severity. **Never re-tag or move a tag** —
roll forward by cutting a new tag (Rule 12: fail visibly).

### Tier 1 — canary/beta regression (no stable impact yet)

1. Close the GitHub prerelease (or delete the prerelease asset; the tag stays
   as a historical record).
2. Open a tracking issue labeled `regression` against the canary/beta tag.
3. Fix on `main`; the next canary build carries the fix automatically.
4. No stable user is affected — stable channel untouched.

### Tier 2 — stable regression (users already upgraded)

1. **Pin the distribution surfaces back to the last known-good stable tag.**
   - Homebrew: revert the formula `version`/`sha` to the previous stable tag
     and push the tap. Existing installs keep their binary; new installs get
     the known-good version.
   - Direct `install.sh`: there is no "revert latest" for GitHub Releases, so
     cut a **patch revert tag** instead (next step).
2. **Cut a patch revert release.** Revert the offending commits on `main`,
   bump patch version, run full CI, cut `v{prev}.patch` stable tag. This
   becomes the new `releases/latest` and the new formula target. This is
   faster and cleaner than trying to un-publish a GitHub Release.
3. **Communicate.** Add a `⚠️ Retracted` note to the bad release's GitHub
   Release body and post to the announcement channel. Users who already
   installed the bad version run `fusion upgrade` (or `brew upgrade`) to move
   to the patch revert.
4. **Post-mortem.** Open a `postmortem` issue: root cause, why the canary gate
   missed it, gate improvement. Required before the next minor release.

### Hotfix flow

For a security fix that can't wait for the canary→beta→stable path: cut the
fix on `main`, then cut a `stable` patch tag directly, skipping canary. This
is the documented exception. The CHANGELOG must note the fast-path and the
CVE/issue it closes.

## 6. Observability & Gating Signals

A local CLI has no always-on telemetry, so gating signals come from three
opt-in / passive sources. The release operator (a human, reviewing before
promotion) is the gate; automation only *gathers* signals, it does not
auto-promote.

### Signal sources

1. **Opt-in crash report.** If a future `fusion` build implements opt-in
   crash reporting (config flag `report.crash = true`, off by default per
   the privacy posture), crashes funnel to a simple counter endpoint. Until
   then this source is empty and the gate relies on the other two.
2. **Issue tracker.** GitHub issues tagged `bug` or `regression` against a
   canary/beta tag. The release operator runs a saved issue query
   (`label:regression,label:bug,tag:canary-vX`) before each promotion.
3. **Local doctor + audit verify.** Users on the canary channel are asked to
   run `fusion doctor` (now includes backpressure circuit-breaker state from
   #52) and `fusion audit verify` (hash-chain integrity from #51). A broken
   audit chain or stuck-open breaker reported against a canary tag blocks
   promotion.

### Gate criteria (promotion checklist)

A candidate advances to the next stage only if ALL hold:

- [ ] No open `regression`/`bug` issue references the candidate tag.
- [ ] `cargo deny check advisories` is clean (no new un-ignored CVE).
- [ ] At least one canary-channel user reports a clean `fusion doctor` +
      `fusion audit verify` on the candidate.
- [ ] CHANGELOG entry for the version is written and reviewed.
- [ ] (For stable only) beta soak ≥ 24h with no new blocking issue.

### Auto-halt

The only automated halt is CI failure — a failing check (`test`/`clippy`/
`deny`) on the tag commit blocks the GitHub Release workflow from publishing.
All other gates are human-reviewed because the signals are human-originated
(issue reports, doctor output). Pretending to auto-decide on absent telemetry
would be a silent failure (Rule 12).

## 7. Implementation Checklist

Concrete steps to adopt this strategy. Owned by CI/CD, not `fusion-cli` Rust
code — no CLI source changes required.

### 7.1 Canary build workflow (`.github/workflows/release-canary.yml`)

Add a workflow triggered on push to `main` (after `ci.yml` passes):

- `needs: [check, test, fmt, clippy, deny]` (reuse the gates from `ci.yml`,
  or run `ci.yml` as a required check first).
- Build `--release`, produce the binary artifact.
- Generate tag `canary-v{version}-{YYYYMMDD}-{SHORTSHA}` from `Cargo.toml`
  version + commit metadata.
- Create a GitHub Release marked `prerelease: true`, attach the binary.
- Do NOT touch the Homebrew formula or `releases/latest`.

### 7.2 Beta/stable cut (`.github/workflows/release.yml`)

Triggered on a new tag push matching `v*` or `v*-beta.*`:

- Run full CI gates.
- Build `--release` (macOS +, optionally Linux for remote use).
- Create GitHub Release: `prerelease: true` for `beta.*`, `false` for a plain
  `v*` stable tag.
- Attach binary artifact + `Cargo.lock` (reproducibility, per #53).
- On stable: optionally trigger a tap-repo workflow to bump the formula
  `version`/`sha`.

### 7.3 Install script channel support (`install.sh`)

- Read `FUSION_RELEASE_CHANNEL` (default `stable`).
- Resolve tag pattern: `stable` → `releases/latest`; `beta` → latest
  `v*-beta.*` prerelease; `canary` → latest `canary-*` prerelease.
- Fetch matching asset, verify SHA256 (from the GitHub Release asset digest),
  install to `/usr/local/bin/fusion`.

### 7.4 Homebrew tap

- Separate formulae or one parameterized formula: `fusion-cli` (stable),
  `fusion-cli@beta`, `fusion-cli@canary`.
- Stable formula version bumps are a manual PR to the tap repo after a stable
  release (the delayed bump is the gray-release soak window, §4).

### 7.5 CHANGELOG + version bump

On each release (canary/beta/stable):
- Update `CHANGELOG.md` with the version, date, and changes (English per
  CLAUDE.md README English-only rule; CHANGELOG is English).
- Bump `Cargo.toml` `[package].version` to match the tag *before* tagging
  (version source of truth = `Cargo.toml`, tag must match).

### 7.6 Adoption order

1. Canary workflow (#54 deliverable — this doc is the spec).
2. Stable release workflow + tap bump.
3. Beta channel (can be added later; canary→stable also works for a small
   project). Beta is optional polish, canary is the required safety net.
